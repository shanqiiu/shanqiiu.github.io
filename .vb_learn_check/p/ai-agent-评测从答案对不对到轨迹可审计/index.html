AI Agent 评测：从"答案对不对"到"轨迹可审计"

Agent评测 轨迹评估 GUI Agent LLM 过程奖励模型

一篇技术随笔，梳理近几年 Agent 评测方法的演进，重点讨论 GUI / 手机 Agent 的轨迹与过程评测如何自动判定，并分享我在一个 GUI Agent 执行评估实践中的思路、借鉴与踩坑经验。

日期：2026-08 · 主题：Agent Evaluation / Trajectory Evaluation / GUI Agent

引言：为什么"成功率"不够用了

早期的 Agent 评测问题很好回答：给一个任务，看最终答案对不对。Exact match、测试是否通过、页面是否到达目标态，一个数字就完成了评估。这个范式简单、客观、可自动化，支撑了从静态问答到工具调用的一大批 benchmark。

但当我们把 Agent 真正放进手机、网页、代码库这种有状态、有副作用、有长程依赖的环境里，“最终结果对不对"这个维度就开始失真了。一个 Agent 用 53 次工具调用、其中 20 次重复搜索才完成任务，和另一个 8 次调用就完成的 Agent，在"成功率"上完全不可区分。更糟的是，成功率无法回答下面这些真实问题：

  • Agent 是真正完成了任务，还是碰巧利用了 benchmark 的漏洞？
  • 它是否点错了一个控件之后自己恢复过来了？
  • 它是否执行了危险操作，只是最终被环境回滚掩盖了？
  • 两个都"成功"的 Agent，哪个更高效、更可靠、更省成本？

所以近几年的 Agent 评测出现了一个清晰的方向迁移：从压缩成单一成功率的静态评测，转向对任务、轨迹、成本、安全和泛化的联合评测。本文将沿着这条线梳理方法脉络，并落到最棘手的场景——只有"执行日志 + 每一步截图"的手机 GUI Agent，过程评测应该怎么做。

一、评测范式的四次迁移

把文献按时间摆开，能清楚看到评测对象在逐步"变厚”：

阶段 评测对象 代表工作
静态问答 单轮答案正确性 传统 NLP benchmark
单步工具调用 是否能选对工具、传对参数 早期 tool-use 评测
多步环境交互 在交互式环境中的推理、规划、决策 AgentBench、WebArena
真实多模态长程任务 视觉理解 + 真实网页/手机 + 长工作流 GAIA、VisualWebArena

AgentBench（arXiv:2308.03688）较早把"LLM 作为 Agent"从静态问答里单独拎出来，在多种交互环境中评测推理、规划、决策和工具使用[1]；WebArena（arXiv:2307.13854）构建了包含搜索、购物、论坛等真实网站的可执行环境，奠定了 Web Agent 评测的常用范式[2]；VisualWebArena（arXiv:2401.13649）进一步说明网页 Agent 不能只看 DOM 文本，还必须处理截图、布局和视觉状态[3]；GAIA（arXiv:2311.12983）则把任务推向"通用个人助理"——需要多步推理、网页浏览、工具调用、多模态理解和现实知识的复杂问题[4]。

这个演进在综述里被系统化。《Survey on Evaluation of LLM-based Agents》（arXiv:2503.16416）和 《Evaluation and Benchmarking of LLM Agents: A Survey》（arXiv:2507.21504）都强调：评测维度不应是单一结果分数，而应覆盖任务完成、工具使用、交互轨迹、长程规划、成本效率和安全性[5][6]。

一句话概括趋势：从"能不能完成一个预先定义的任务"，转向"能不能在不确定、变化且具有真实代价的环境中持续、可靠、安全地完成工作"。

二、一个可用的五层评测框架

综合这些工作，可以把 Agent 评测拆成五层，每一层回答不同的问题：

  1. 结果层：任务最终是否完成？——用环境最终状态、持久化副作用、测试是否通过来判定。
  2. 能力层：哪类能力成功或失败了？——规划、工具选择、Grounding、视觉理解、错误恢复分别拆开看。
  3. 过程层：轨迹是否合理、合规？——动作是否合法、是否循环、是否绕路、是否遵循操作顺序与权限。
  4. 效率层：用了多少资源？——动作数、时间、token、工具调用、重试、人工介入。
  5. 可靠层：是否安全、稳定、可泛化？——越权、危险副作用、重复运行方差、环境变化、提示注入。

对应地，评测结果也不应该再是一个标量 Score = SuccessRate，而是一个向量：

1

AgentScore = (Success, Efficiency, Reliability, Safety, Recovery)

值得注意的是，这五层里最难自动化、也最被低估的是过程层（第 3 层）。结果层有环境验证器兜底，能力层有 benchmark 拆分，效率层靠统计，但"这个过程到底合不合理"长期依赖人工看轨迹。接下来重点讨论它如何自动判定。

三、轨迹与过程评测：自动判定怎么做

社区一个普遍的误区是"直接让 LLM 看完整轨迹打个分"。这个做法简单，但很不稳定——judge 模型会偏好更长更啰嗦的轨迹、会被漂亮但错误的解释误导、看不出工具调用的真实副作用。更可靠的做法是分层自动判定：能形式化的用确定性验证，能从日志算的不要交给模型，只有开放式过程质量才交给 LLM judge 或过程奖励模型。具体有下面五类方法。

3.1 确定性环境验证

可靠性最高的一类：不评价 Agent 说了什么，直接检查环境是否达到目标状态——文件是否被正确创建、数据库记录是否符合预期、购物车是否加入了正确商品、代码是否通过测试。

GroundEval（arXiv:2606.22737）代表了把 Agent 搜索、获取证据、引用来源等行为转化为确定性检查的方向，核心思想是：能从环境和执行日志直接验证的内容，不应该交给 LLM 主观判断[7]。这类方法的优点是客观、便宜、可复现；缺点是只能判断"结果对不对"，无法判断"过程是否合理"，Agent 可能通过不允许的捷径完成任务。

3.2 规则、有限状态机与时序逻辑

如果任务有明确流程，可以把允许和禁止的行为写成规则或时序逻辑。比如报销流程要求"先核验金额，再提交付款"，自动判定器就可以检查：是否在审批前触发了付款、是否访问了禁止数据、是否重复提交。

AgentLTL（arXiv:2607.02599）把程序约束表示为时序逻辑，用于验证、约束和训练工具型 Agent，特别适合医疗、金融、企业审批这类"过程本身就是正确性的一部分"的场景[8]。时序规则可以表达先后关系（必须先 search 再 download）、禁止关系（未授权不能 delete）、数量关系（最多重试三次）、依赖关系（验证身份后才能访问账户）。

3.3 轨迹结构与行为统计

不判断语义质量，只从轨迹提取行为特征：工具调用次数、无效动作比例、重复动作次数、失败后恢复步数、是否出现循环、是否提前终止。可以定义一些简单指标：

1
2
3

Efficiency    = 有效动作数 / 总动作数
LoopRate      = 重复状态或重复动作次数 / 总动作数
RecoveryRate  = 失败后最终恢复的轨迹数 / 出现失败的轨迹数

这类方法特别擅长发现"最终成功但过程很差"的情况。AgentLens（arXiv:2607.06624）代表从单一结果指标转向生产轨迹评价的方向，强调对 coding Agent 的交互轨迹进行评审而不是只记录最终是否通过测试[9]；《Failure as a Process》（arXiv:2607.09510）则专门剖析 CLI coding Agent 失败轨迹中的过程模式和失败演化[10]。

3.4 LLM-as-a-Judge：边界在哪里

对于"这个工具调用是否合理"“这个计划是否充分"“这个错误恢复是否有效"这类开放问题，规则不够用，可以让另一个 LLM 当评审器。常见做法包括逐步评分、阶段评分、整体评分、成对比较、带参考轨迹评分、事实核验。

但它不应作为唯一裁判。更好的分工是：

硬事实由环境验证器判定，软质量由 LLM judge 判定。

3.5 过程奖励模型（PRM）

PRM 不是只看最终结果，而是给每一步或每个中间状态分配质量分数：

1

R_process(τ) = Σ r(s_t, a_t, s_{t+1})

它既能用于评测，也能用于轨迹排序、训练 Agent、在线拦截低质量动作、预测任务是否失败。《A Survey of Process Reward Models》（arXiv:2510.08049）对这一类方法做了系统梳理[11]。但 PRM 的标注成本高，且模型可能学会"看起来合理"的行为模式，实际系统通常把它与环境奖励、工具规则和最终结果结合使用，而不是单独使用。

四、GUI / 手机 Agent 的轨迹评测：状态—动作—状态

最贴近工程实践的场景是：只有 Agent 执行日志 + 每一步操作前后截图，如何做过程评测。近期工作已经朝这个方向走：GUIDE（arXiv:2604.04399）强调对 GUI Agent 轨迹做可解释的分层诊断[12]；VisCritic（arXiv:2606.24525）把视觉状态比较用作逐步过程奖励[13]；StepReflect（arXiv:2608.05587）关注移动 GUI 的结构化界面转移反思[14]。

核心思路是把每一步建模为一个状态转移单元：

1

e_t = (I_t, a_t, I_{t+1}, l_t)

其中 I_t 是动作前截图，a_t 是动作，I_{t+1} 是动作后截图，l_t 是日志（坐标、控件、模型输出、耗时）。整条轨迹就是这些单元的序列。评测不应只输出"成功/失败”，而应输出：最终结果 + 每步动作评分 + 界面转移评分 + 任务进展评分 + 错误恢复评分 + 效率评分 + 安全违规 + 失败根因。

4.1 截图是部分观测，不是真值

这是最容易被忽视的一点。截图单独存在几个问题：看不到控件真实可点击区域、看不出控件是否 enabled、同样的视觉界面可能对应不同内部状态、小图标和滚动位置容易误判、有些状态变化前后截图几乎一样。

所以应把截图视为对真实 UI 状态的部分观测：o_t = Observation(s_t)。可靠的评测要先把截图转成结构化 UI 状态（页面类型、控件列表、控件状态、弹窗、主要文本），优先结合三类信息：截图视觉信息、操作日志、系统/无障碍树（Accessibility tree、UIAutomator hierarchy）。若无法拿到 UI tree，也要明确记录"当前是视觉-only 证据”，而不是假装有结构真值。

4.2 动作 Grounding：是否命中正确目标

对每步动作，评估三件事：Agent 想操作什么、实际操作了什么、该操作是否符合任务当前阶段。动作定位准确率可以定义为：

1

ActionGrounding = Σ 1[实际命中目标控件] / T

这里要特别区分两种失败：意图正确、坐标错误（知道该点"允许"但点偏了）是 grounding 问题；意图错误、坐标准确（精准点中了不该点的控件）是 planning/policy 问题。二者修复方式完全不同，混为一谈会误导后续优化方向。

4.3 界面转移验证：动作是否产生了正确变化

单步动作最重要的不是"看起来合理"，而是是否导致正确的 UI 转移。可以把每一步分成四种情况：

类型 动作 界面变化 解释
有效推进 合法 目标状态变化 最理想
无效动作 合法 没有有效变化 点偏、页面未加载或操作无效
错误推进 合法 进入错误页面/改变错误状态 规划或目标识别错误
危险推进 不应执行 产生敏感/不可逆副作用 安全违规

界面变化又可细分为导航变化、内容变化、控件状态变化、输入变化、外部副作用五类。其中外部副作用（发消息、提交订单、删除文件、授权）必须最严格——不能仅凭截图里出现"成功"就认定成功，要尽量验证外部状态（重开页面、查列表、查订单、读文件系统）。

4.4 里程碑进展：页面变了 ≠ 任务推进了

不是所有界面变化都代表任务进展。Agent 在设置页之间来回切换，截图变化很大，但任务没推进。最实用的方法是为任务定义一组子目标/里程碑，每步判断已满足哪些：

1

P_t = Σ w_i · 1[m_i achieved at t] / Σ w_i

进展分数是非单调的（误操作会导致回退），因此可以识别有效推进（ΔP>0）、无效操作（ΔP=0）、回退（ΔP<0）、“局部成功但整体无效”。固定任务里程碑可手工定义，开放任务可由模型生成候选再交给规则/环境验证确认。

4.5 循环与恢复检测

手机 Agent 常见的问题不是一次严重错误，而是点错后继续执行、页面没变化却重复点击、搜索无结果后重复相同搜索、权限弹窗出现后无法恢复。重复动作检测要满足"重复动作模式 且 状态没有有效变化"双条件，否则会误伤合理的重试和列表滑动。恢复检测则识别 Agent 是否：发现错误 → 改变策略 → 回到可恢复状态 → 最终继续完成，并记录恢复代价（从错误到恢复的动作数）。一个每次错误都要 20 步才能恢复的 Agent，即使最终成功，也不适合真实部署。

4.6 VLM 结构化评审

VLM 适合判断截图中的开放问题：当前界面是否满足某子目标、动作后是否出现预期 UI、是否误解了弹窗。但不要让它直接生成自由文本分数，而要输出结构化 JSON：

1
2
3
4
5
6
7
8
9

{
  "target_correct": true,
  "transition_expected": true,
  "task_progress": 0.8,
  "state_regressed": false,
  "unsafe": false,
  "reason_code": null,
  "confidence": 0.91
}

每次给 VLM 的输入应包括：任务目标、当前任务阶段、动作前截图、动作后截图、动作类型和参数、Agent 的动作意图、已完成的里程碑、可选的 UI tree/OCR 结果。关键是前后帧一起给——单张截图缺少因果信息，无法判断动作是否有效。

五、硬评测 + 软评测双通道与硬门控

把上面的方法组合起来，推荐的设计是"硬评测 + 软评测"双通道，以及一个门控逻辑：

  • 硬评测（规则、UI tree、OCR、状态机、系统日志）：点击坐标是否命中控件、是否进入目标页、输入是否正确、是否授权、是否发生危险操作、是否违反动作顺序。
  • 软评测（VLM / LLM judge）：动作是否符合任务策略、页面是否与阶段匹配、错误恢复是否合理、是否明显绕路。

最终判定不要简单平均，而用门控：

1

Pass = FinalGoalVerified  ∧  NoCriticalSafetyViolation  ∧  EvidenceSufficient

通过后再报告质量分（进展、效率、恢复、Grounding 的加权），或者报告"成功率—成本"曲线。安全违规应当是硬失败，而不是普通扣分——即使 Agent 最终完成任务，只要越权访问了数据，也不能判定为成功。这一设计原则在工具型 Agent 的安全评测里被反复强调，例如 SafeClawBench（arXiv:2606.18356）把语义层面的不安全行为、审计证据和沙箱中的实际危害分开对待[15]。

六、评测器本身也要被评测

一个容易被忽略的事实是：评测器也是软件，也会错。如果只报告 Agent 分数、不报告 evaluator 的误差，就会把评测器的偏差误认为 Agent 的缺陷。至少应该报告：

  • 任务成功判定的 Precision / Recall / F1；
  • 每类异常检测的 Precision / Recall、首错定位偏差；
  • VLM judge 与人工的一致率及分桶结果；
  • uncertain 覆盖率、人工复核率和误拒率；
  • 同一轨迹重复评审的一致性；
  • 每任务延迟、模型调用、token 和货币成本；
  • 按 App、任务长度、语言、弹窗/网络异常、证据缺失程度分桶的表现。

这条原则也回应了另一个隐患：benchmark 泄漏。如果任务、网页或代码库被训练数据记住，分数就不再代表泛化能力，因此需要隐藏测试集、动态生成任务、模板族隔离和时间外测试。

七、我的技术实践与经验总结

下面分享我在一个 GUI Agent 执行轨迹自动评估 实践中的设计思路、对上述文献的借鉴方式，以及踩坑后的经验。为避免把问题扯到具体实现上，我只谈方法与取舍，不涉及代码和具体数据。

7.1 两阶段判定：意图召回在前，执行验证在后

我借鉴了 GUIDE 的分层诊断 和 AutoEval（arXiv:2503.02403）的"子状态分解 + 判官流水线"思路，把每个关键检查点判定拆成两阶段：

  1. 意图召回：先判断 Agent 是否"尝试过"这个必要子状态（有没有对应的实际意图候选）。这回答"规划/目标理解有没有问题"。
  2. 执行验证：只在召回到候选之后，才用真实截图验证"这个正确意图是否真正在界面上生效了"。这回答"执行有没有阻塞"。

这个拆分的价值在于能把两种截然不同的失败分开：没有对应意图（规划缺失）和有意图但状态没达成（执行失败）。二者对应完全不同的优化手段——前者改规划，后者改 grounding 或环境处理。意图未召回时，不强行分配截图、不做无意义的视觉调用，直接标记为 unmatched_intent。

7.2 子状态分解：路径无关、原子、可观察

任务分解时我坚持三个原则，而不是"按步骤数量均匀切 checkpoint"或绑定某条固定操作路径：

  • 路径无关：描述"结果状态"，不限定点击哪个坐标、经过哪个页面。Agent 用不同入口、快捷方式达到相同状态都不算失败。
  • 原子：一个检查点只承载一个状态边界，不把"搜索 → 筛选 → 进详情"这种复合阶段塞进一项。
  • 可观察：能通过截图、OCR、页面结构或系统状态验证。

这也意味着"点击搜索框"“输入关键词"这类操作不是检查点，“搜索结果已展示"“筛选条件已生效"才是。Agent 可能通过语音、快捷入口达到相同状态，评估系统不应因为路径不同而误判失败。这一点与 WebArena/VisualWebArena 的"环境状态验证"范式一脉相承——评估状态，而不是评估某一种操作路径。

7.3 证据分层与不确定输出

我把证据分成了几个信任等级：结构事实（动作类型、步骤索引）> 客观观测（OCR、截图差分、页面文本）> 模型判断（页面描述、VLM 判定）> Agent 自述（操作意图）。核心纪律是：

  • Agent 的意图自述（“我想做什么”）只是召回信号，不是真值，不能独立证明任务完成。
  • 截图相似度不能当状态正确性，像素变化只是"发生了变化"的信号，不是"变对了"的证明。
  • 缺证据必须输出 uncertain，不能静默判成功。这是我对"不确定传播"最看重的一条：规则不能确定、VLM 置信度低、截图缺失，都不能被解释成"正常”。

这条纪律的来源，正是 GroundEval"能从环境直接验证的不要交给 LLM"和 SafeClawBench"把审计证据单独拆开"的思想。

7.4 安全作为硬门控，而不是扣分项

统一结论我采用门控逻辑而不是加权平均：通过 = 目标已证实 ∧ 无关键安全违规 ∧ 证据充分。安全事件（越权、危险副作用、违反顺序/禁止约束）是硬失败，不能用一个高的过程分把它稀释掉。这与五层框架里"安全违规是硬失败而非普通扣分"的原则一致，也呼应了 AgentLTL 用时序约束验证过程合规的思路。

7.5 成本治理：VLM 调用是绝对瓶颈

实践中最大的工程体感是：VLM 调用是评估流水线的绝对瓶颈，而不是规则计算。于是我把"能不算就不算"落成了三条纪律：

  1. 缓存：以 模型 + 提示词 + 图片哈希 做 key 缓存 VLM 响应，重复评估命中缓存后模型调用归零。
  2. 并发：VLM 调用是 I/O 密集，天然适合线程池并发，串行改并发能带来接近线性的加速。
  3. 分层送审：规则能判的（坐标命中、动作次数、重复、耗时、权限）绝不让模型算；只把规则无法确定的片段送给 VLM，并且尽量复用 Agent 执行时自己已经产出的页面理解，避免重复调用。

这三点背后的方法论很简单，也是 3.1—3.5 的浓缩版：能形式化的用确定性验证，能从日志算的不要交给模型，只有开放式过程质量才交给 judge。

7.6 经验教训小结

  1. 成功率是必要的主指标，但绝不是唯一指标。过程、效率、恢复、安全、证据质量必须并排出现。
  2. 截图是观测不是真值。优先抽 UI 语义和控件状态，不要把像素相似度当成功。
  3. 前后帧一起判，单帧没有因果。判断动作有效性必须给 before/after。
  4. 任务进展用里程碑表示。“页面变了"不等于"任务推进了”。
  5. 别让 VLM 算它可以直接算的东西。规则层越厚，judge 越稳、越便宜。
  6. 安全是门控不是扣分。越权 + 完成任务 ≠ 成功。
  7. 评测器要被评测。没有金标、没有 Precision/Recall、没有 judge 一致性，评估结果不可信。
  8. 过程评测的价值不只是给分，而是定位首错。用户真正想要的是"Agent 为什么失败、第一步错在哪”，不是一个总分。

八、总结与展望

把整条脉络收束成一句话：

Agent 评测正在从"静态答案正确性”，转向"动态环境中的任务、轨迹、成本、安全和泛化的联合评测"，而过程评测的核心不是训练一个更强的 judge，而是先构建一个可验证的 UI 状态表示和任务里程碑表示。

一个稳健的评测系统，应当是"环境验证器（结果是否真的完成）+ 规则验证器（是否违反流程/权限/安全）+ 轨迹分析器（是否低效/循环/恢复失败）+ LLM/VLM judge（开放语义质量）+ 人工复核（高风险或难形式化的案例）“的组合，并用 目标门控 ∧ 安全门控 ∧ 证据门控 输出结论，而不是一个不透明总分。

未来值得持续关注的方向包括：统一评测基础设施（如 AgentCompass，arXiv:2607.13705）对碎片化 benchmark 的整合[16]；多 Agent 系统的公平比较——不能只比 Agent 数量，要比"质量/成本”（如《Do More Agents Help?》，arXiv:2606.05670）[17]；以及软件工程 Agent 从"issue 是否解决"扩展到完整工作流（如 SWE Atlas，arXiv:2605.08366）[18]。对我们这些做工程落地的人而言，最重要的下一步不是追更热的模型，而是把评测器自己的效度（金标、一致性、成本）先做扎实——否则任何 Agent 分数都只是自说自话。
