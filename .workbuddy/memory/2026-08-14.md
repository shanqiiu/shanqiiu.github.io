## 今日访客真实化（Vercel KV 自建函数）
- 结论：vercount（及不蒜子）公开 API **只给累计** `site_uv/site_pv/page_pv`，**无"今日"数据**，故无法复用。
- 方案（用户选 Vercel KV）：新增 `api/today-visitor.js`（Vercel Node Serverless Function，GET `/api/today-visitor`）。逻辑：取访客 IP → SHA-256 哈希（不存明文 IP）→ `SADD` 进当日集合（按 UTC 日切分 key `site:visitors:YYYY-MM-DD`）做去重，`EXPIRE 30d` 防无限增长，`SCARD` 即今日独立访客数；底层走 Upstash Redis REST API（Bearer）。
- `main.js` 的 `initVisitorStats()` 改为 `fetch('/api/today-visitor')` 显示真实数字；失败/未配置时回退 `--`。
- 部署依赖：**需在 Vercel 控制台绑定一个 KV Database** 到本项目，绑定后自动注入 `KV_REST_API_URL`/`KV_REST_API_TOKEN` 等环境变量，重新部署即生效；未绑定时接口返回 `count:null`，前端显示 `--`（不报错）。
- 验证：`node --check` 语法 OK；`hugo --minify` 构建通过，`/api/today-visitor` 进入 JS bundle、footer 在首页正常渲染。
- 提交：`d86082a` 已推 `origin/master`（含 footer 建站日期 `2026-08-01` + main.js + api 函数）。
- **KV 找不到的替代**：Vercel KV 即 Upstash 封装，函数已兼容 Upstash REST（POST JSON `{"command":[...]}` + Bearer token）。直接用 upstash.com 免费 Redis 实例，在 Vercel 项目 Settings → Environment Variables 设同名的 `KV_REST_API_URL` / `KV_REST_API_TOKEN`（取 Upstash 的 REST API Endpoint 与 REST API Token），Redeploy 即生效，**代码零改动**。
- **最终落地方案（用户改选 Supabase）**：放弃 KV/Upstash，改连项目已有的 Supabase（Vercel Storage → Supabase Integration，prefix=STORAGE）。`api/today-visitor.js` 已改写为 Supabase 版：`findSupabaseEnv()` 鲁棒读取 `STORAGE_*`/`SUPABASE_*`/`KV_*` 前缀的 supabase URL+key（优先 service_role），调用 RPC `public.count_today_visitor(p_day, p_hash)`（security definer，insert+count 去重）；`supabase/schema.sql` 新增 `daily_visitors` 表 + 该 RPC（grant execute to anon/authenticated）。提交 `cfb6895`。生效前提：在 Supabase 执行 schema.sql、Vercel Redeploy。

## 今日访客「--」排查（诊断日志 e4c0917）
- 现象：首页显示 `--`。为定位，给 `api/today-visitor.js` 加 `console.error` 诊断（env-not-found / rpc-failed / fetch-error），提交 `e4c0917`。
- Vercel Functions 日志结论：`rpc failed: 404 PGRST202 Could not find the function public.count_today_visitor(p_day, p_hash)` → **环境变量与 Redeploy 均正常**（否则会先报 env-not-found），根因是 **Supabase 未执行 schema.sql 的 daily_visitors 段（表 + RPC 没建）**。
- 解决：Supabase SQL Editor 执行 `daily_visitors` 建表 + `count_today_visitor` RPC（已附最小独立脚本），无需改代码/重部署，刷新首页即出数；若仍 404 跑 `notify pgrst, 'reload schema';` 重载 schema cache。
- 教训：Vercel Supabase Integration 只注入连接变量，**不会自动建业务表/RPC**；每次新增数据库对象都要手动在 Supabase 执行对应 SQL。
- Vercel Storage Integrations（Supabase/Neon/Mongo）**不支持"换绑到同一个供应商的另一个项目"**，无 Change project 选项，只能整体 Remove。但若项目级 Integrations 没显示 Disconnect/Manage，是因为显示在 **Vercel 团队级 Integrations**（路径 `vercel.com/dashboard/integrations`），那里有 Installed Products 列表（项目显示名可能是 `supabase-yellow-lens` 而不是 `shanqiiu-blog`，但其实是同一个项目）。
- 切到"老项目"的最干净办法：**保留现有集成不动**，在 Vercel 项目里**手动加 3 个 `SUPABASE_*` 变量**（URL/ANON_KEY/SERVICE_ROLE_KEY，填老项目），`api/today-visitor.js` 的 `findSupabaseEnv()` 优先级 `SUPABASE_*` > `STORAGE_*` > 兜底。提交 `f43d666`。
- 用户确认：之前部署"新增资源"（聊天室等）时已手动配过 `SUPABASE_URL`+`SUPABASE_ANON_KEY`（Production）指向**老项目**（23h ago）；后来连 Vercel Storage 集成注入 `STORAGE_*` 指向新项目 `vliefowmirfbxpkpekqs`。最终用户**删了新项目、重新处理环境变量**。
- **真正根因（代码 bug，非环境变量）**：`findSupabaseEnv()` 对变量名 `SUPABASE_URL` 做前缀提取 `k.replace(/_?(SUPABASE_URL|URL)$/i,'')` 得到空串，导致拼接 `_ANON_KEY`/`_SERVICE_ROLE_KEY`（开头多下划线）永远匹配不到 `SUPABASE_ANON_KEY`，函数报 `env not found`。之前 STORAGE 能跑是 `STORAGE_SUPABASE_SERVICE_ROLE_KEY` 候选碰巧对上的侥幸。修复：前缀为空/为 SUPABASE 时统一回退 `SUPABASE` 前缀；用 node 单元测试验证 case1(SUPABASE only)/case2(两者共存 SUPABASE 优先)/case3(STORAGE only) 全部正确。提交 `c8b37f5`。老项目仍需补建 daily_visitors 表 + count_today_visitor RPC（之前只建在被删的新项目）+ Redeploy。
- Vercel Supabase Integration 实际注入的变量（custom prefix=STORAGE 实测）：`STORAGE_SUPABASE_URL`、`STORAGE_SUPABASE_ANON_KEY`、`STORAGE_SUPABASE_SERVICE_ROLE_KEY`、`STORAGE_SUPABASE_SECRET_KEY`、`STORAGE_SUPABASE_JWT_SECRET`、`STORAGE_SUPABASE_PUBLISHABLE_KEY`；以及 `STORAGE_POSTGRES_*`（HOST/URL/PASSWORD/USER/DATABASE/PRISMA_URL/URL_NON_POOLING）；前端可用的 `NEXT_PUBLIC_STORAGE_SUPABASE_URL/_ANON_KEY/_PUBLISHABLE_KEY`。**无** `STORAGE_URL` 这种短名。`api/today-visitor.js` 的 `findSupabaseEnv()` 兼容上述命名。
- 用户确认其 Supabase **多项目结构**：聊天室/资源等已有数据库在**老项目**（网站业务数据所在）；Vercel 曾单独连接 `vliefowmirfbxpkpekqs`（ref=`vliefowmirfbxpkpekqs`，区域 ap-northeast-1）这个**空项目**用于今日访客，故 `api/today-visitor.js` 最初只认此项目（STORAGE_SUPABASE_URL 指向它），表/RPC 也建在这 → 已验证可显示数字。
