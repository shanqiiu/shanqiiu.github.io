## 聊天室功能边界澄清（用户反馈两个局限）
- 用户反馈：① 聊天室没有实现实时交互；② 每次登录需要重新注册。
- 根因（已向用户讲清，非 bug）：聊天室是纯客户端实现，消息存 `localStorage` + `BroadcastChannel`（仅同浏览器多标签同步），无云端后端。
  - 实时仅覆盖「同一浏览器开多个标签」；跨浏览器/跨设备/跨用户看不到彼此消息。
  - 昵称存 `localStorage[chat:userName]`（同浏览器刷新不丢），但换浏览器/设备/清缓存即丢失 → 体验上像"每次都要重注册"，且无非真正的账号体系。
- 升级方案建议：Supabase（BaaS，Postgres+Realtime+Auth，免费额度够个人站，与 Vercel 静态站契合），可同时解决真·实时+跨设备持久化+跨设备免重输。备选 Pusher。
- **用户决策（2026-08-13）：暂不改，先聊清楚现状，不接 Supabase 后端。** 未来若再提"实时聊天"可直接引用此结论。

## 聊天室接入 Supabase（同日下午，用户改主意要"用supabase实现部署"）
- 已落地：把聊天室从纯本地升级为「双模式」——Supabase(云端实时) / 本地(BroadcastChannel 回退)，由运行时 `window.SUPABASE_CONFIG` 是否存在自动切换。
- 改动文件：
  - `assets/js/chat.js`：重写。Supabase 模式=Postgres 持久化 + `postgres_changes` 实时订阅(自己发的消息用 `userId===self.userId` 去重避免重复) + Presence(`online:<room>` channel)统计在线人数；本地回退不变。乐观更新+失败回滚。
  - `layouts/partials/head.html`：`{{ if eq .Section "chat" }}` 内用 `os.Getenv "SUPABASE_URL"` / `os.Getenv "SUPABASE_ANON_KEY"` 注入 `window.SUPABASE_CONFIG`，并仅在配置存在时加载 `supabase-js@2` CDN（顺序：配置→SDK→chat.js，保证 chat.js 运行时 `window.supabase` 已就绪）。
